# 中继服务器 + 局域网双通道同步 设计文档

> 状态：草案（未实施）。目标是在**不改动现有 LAN 同步行为**的前提下，
> 新增一条「自建中继服务器」通道，两条通道同时激活、各自独立收发、统一入库去重。

## 1. 背景与目标

现有局域网同步（`src-tauri/src/lan.rs`）依赖 UDP beacon 发现 + 直连 HTTP（8765），
设备不在同一网段时完全不可用。本设计新增一条中继通道：

- 自建一台公网可达的服务器（VPS / NAS），各设备主动与之保持 WebSocket 长连接。
- LAN 与 Relay **同时存在、各走各的**：本机剪贴板变化同时往两条通道发；
  收到的条目统一走现有入库口去重，先到先存，晚到的自动判重。
- LAN 通道代码零改动（或接近零改动），Relay 作为独立模块新增。

## 2. 总体架构

```
                ┌── LAN 通道（lan.rs 现状）── 直连 ──> 局域网设备
本机剪贴板事件 ──┤
                └── Relay 通道（新增 relay.rs）── WSS ──> 中继服务器 ──> 远端设备
                                                                │
                                                          离线暂存队列
                                                          （TTL + 条数上限）
```

- **双发，不做优先级选择**。判断「哪条路通」需要复杂状态机，收益极小；
  文本条目几 KB，双发带宽开销可忽略。图片/大文件可选「仅 LAN 同步」开关（见 §8）。
- 两条通道互为冗余：服务器宕机不影响局域网；离开局域网（如手机切蜂窝）不影响中继。

## 3. 复用现有机制的可行性（已核对代码）

双通道方案能成立，是因为现有 `lan.rs` 的两个设计恰好就是双通道需要的：

### 3.1 去重：按内容哈希，天然幂等

`store_remote()`（lan.rs:2054）入库时按 `hash` 列查重：

- 已存在 → 只把 `created_at` 顶到最新（与安卓端 touch 行为一致），返回「重复」。
- 不存在 → INSERT。

因此同一条剪贴板从 LAN 和 Relay 各到一次时，**晚到的那份自动被判重丢弃**，
无需为双通道新增任何去重逻辑。入库口是幂等的，这是整个方案的地基。

### 3.2 环回防护：按来源设备 ID

- 接收侧（lan.rs:1924）：`remoteDeviceId == 本机 id` → 拒收。
- 发送侧 `/clips`（lan.rs:1047）：`origin == requester` → 不回传。

且 `/clips` 会把**来自第三方的记录**（保留了原始 `remoteDeviceId`）继续提供给
其他设备——即现有协议已支持「传递同步」（A→B→C），中继场景只是换了一条传输路，
语义完全兼容。

### 3.3 需要守住的一条铁律

**只有本机剪贴板变化才触发外发；入库的远程条目绝不再次外发。**
LAN 侧现状如此（监听剪贴板 → 仅本地新条目入待同步集），Relay 侧必须同样遵守，
否则双通道 + 传递同步会放大成回环风暴。

## 4. 中继服务器设计

### 4.1 选型

- 语言随意（Rust/Axum、Node、Go 均可），单二进制 + SQLite/内存队列即可，资源占用极小。
- 传输：**WebSocket over TLS**（WSS）。长连接由客户端发起，NAT/防火墙友好；
  服务器不主动连接任何设备。
- 复用现有线上口径：时间戳毫秒、JSON 字段名与 `/clips` 响应一致
  （`type` / `text` / `timestamp` / `remoteDeviceId` / `remoteId` / `fileName` / `fileSize`），
  客户端收到后可直接复用现有解析函数。

### 4.2 概念模型

- **分组（room）**：同一用户的多台设备属于同一分组。加入凭据 = 分组 ID + 分组密钥
  （设置页填写，或扫码/配对码换取）。
- **设备身份**：沿用现有 `device_id`（`LanSettings.device_id`），全网络唯一。
- **服务器职责**：连接管理、分组内转发、离线暂存、游标记录。**不解析内容语义**
  （配合 §5 加密后，服务器连内容都看不到）。

### 4.3 消息协议（草案）

客户端 → 服务器：

```json
{ "op": "hello",  "deviceId": "...", "name": "...", "group": "...",
  "ts": 1758..., "auth": "HMAC-SHA256(接入密钥, nonce+deviceId+ts)" }
{ "op": "push",   "clip": { "type": 1, "text": "...", "timestamp": 1758...,
                            "remoteDeviceId": "...", "remoteId": 123 } }
{ "op": "pull",   "sinceSeq": 456 }                 // 连接成功后补拉（游标为服务器分配的条目序号）
{ "op": "ping" }
```

服务器 → 客户端：

```json
{ "op": "challenge", "nonce": "..." }          // 连接建立后第一个消息，hello 鉴权用
{ "op": "clip",   "seq": 457, "clip": { ...同 push 的 clip... } }   // seq 为服务器分配的单调递增序号
{ "op": "peers",  "devices": [{ "deviceId": "...", "name": "...", "online": true }] }
{ "op": "acked",  "remoteId": 123, "seq": 457 }                     // push 确认，seq 供发送方推进游标
{ "op": "error",  "code": "auth_failed" }      // 鉴权失败/超时后立即断开
```

### 4.4 离线暂存与游标（M3 已实现）

- 服务器对每条 `push` 暂存一份（SQLite，`data/relay-queue.db`，按分组隔离），
  每条分配单调递增的 `seq`；TTL 7 天（按服务器接收时间），每组上限 5000 条，
  超限淘汰最旧。
- 游标用 `seq` 而非时间戳（避免同毫秒并发漏拉）：设备连接成功（收到 welcome）后发
  `pull {sinceSeq: last_seq}`，服务器把 `seq > sinceSeq` 的暂存条目逐条下发；
  实时 `clip` 与 `acked` 都携带 `seq`，客户端内存中实时推进 `last_seq`，
  断开时统一落盘（`relay.last_seq`）。
- 补拉与实时推送撞车产生的重复，由客户端入库时内容哈希查重（§3.1）兜住。

### 4.5 鉴权（强制，握手第一步）

**原则：不是谁都能连。** 鉴权在连接建立的第一步完成，未通过鉴权的连接直接断开，
服务器不为其分配会话、不接受任何 `push`/`pull`。

- **握手流程**：WSS 建立后，服务器先下发一次性挑战 `nonce`；客户端必须在超时窗口
  （5 秒）内回复 `hello`，携带 `deviceId` + 分组 ID + `HMAC-SHA256(接入密钥, nonce + deviceId + timestamp)`。
  校验通过才进入分组；校验失败或超时直接关连接。时间戳偏差超过 ±5 分钟视为重放，拒绝。
- **密钥不上线**：密钥本身从不传输，挑战-响应防抓包重放；WSS（TLS）全程加密是底层兜底。
- **密钥分层**：
  - **接入密钥**（服务器级）：证明「我是这台服务器的合法用户」，防止陌生人拿
    自建服务器当免费中继。服务器配置可持有多个接入密钥（按用户/家庭区分）。
  - **分组密钥**（房间级）：证明「我属于这个分组」，同时作为端到端加密的根密钥（§5）。
    鉴权通过后服务器只按分组 ID 路由，分组密钥本身不发给服务器（加密场景下
    服务器连分组内明文都不可见）。
- **防爆破**：鉴权失败按 IP 计数，连续失败（如 5 次）临时封禁（如 10 分钟）；
  单 IP 并发连接数上限（如 20）；`hello` 超时强制断开。
- **与 LAN 凭证独立**：Relay 的接入密钥/分组密钥与 LAN 配对码互不相关，各管各的，
  一个失效不影响另一个。
- **进阶（后续迭代）**：复用 6 位配对码交互，由已入网设备通过中继为新设备背书、
  下发分组密钥，替代手工抄密钥。

### 4.6 部署方式：手动运行与 Docker 双支持

服务器做成**单个可执行文件**，三种配置来源：环境变量兜底、配置文件
（`relay-server.json`，exe 同目录）覆盖、命令行参数最高优先级。同一份代码
天然同时支持两种运行方式：

- **手动运行**：各平台编译产物（Windows / Linux / macOS），直接执行
  `./relay-server --port 8780`，无外部依赖。
- **Docker 运行**：同一二进制打入极简镜像（`alpine`/`scratch`，约 10MB），
  参数走环境变量，暂存队列（SQLite）目录挂卷持久化：

```yaml
# docker-compose.yml 示意
services:
  relay:
    image: lscopy-relay:latest
    ports:
      - "8780:8780"
    environment:
      RELAY_PORT: 8780
      RELAY_ACCESS_KEYS: "key1,key2"   # 接入密钥列表（§4.5）
      RELAY_DATA_DIR: /data
    volumes:
      - ./data:/data                    # 暂存队列持久化
    restart: unless-stopped
```

- **TLS 两种姿势**：证书直接挂进容器由服务器终结；或服务器监听明文 8780、
  前面套 nginx/Caddy 反代终结 TLS（家用 NAS 常见），客户端配 `wss://` 地址即可。
- **镜像发布**：已实现——`.github/workflows/relay-image.yml`，推 `v*` tag（或手动触发）
  自动构建并推送 GHCR 多架构镜像（x64 + ARM），标签 `:vX.Y.Z` / `:X.Y` / `:latest`。
- 配置改动首期「重启生效」即可，不做热加载。

## 5. 端到端加密（M4 已实现）

剪贴板常含密码、私钥，自建服务器也不应看到明文：

- **分组密钥**（客户端配置项 `relay.group_key`，可选）：只存在于各设备本地，
  同组设备手工填相同密钥。留空 = 明文模式（向后兼容）。
- 密钥派生：`HKDF-SHA256(分组密钥, salt="lscopy-relay-e2e", info=分组ID)` → AES-256
  密钥。服务器只持有接入密钥，无法派生加密密钥。
- 加密粒度：仅 clip 的文本内容。`AES-256-GCM`，每条随机 12 字节 nonce，
  密文为 `base64(nonce ‖ ciphertext)` 放在 `clip.data`，并带 `enc: 1` 标记。
- **元数据明文 + AAD 绑定**：`remoteDeviceId`/`remoteId`/`timestamp`/`type` 保持明文
  （服务器路由、客户端环回防护都要用），同时作为 AAD——篡改元数据会导致解密失败。
- 接收侧：本机未配分组密钥或解密失败（密钥不一致/数据被篡改）→ 跳过该条目。
- 加密失败时**静默丢弃而不是降级发明文**，避免用户误以为已加密。
- 不要用互传文件那套 XOR 流加密（`xor_crypt_at`）——那是同网段配对联谊的轻量方案，
  防不住服务器端的主动攻击者。
- 密钥轮换、设备退出分组时的剔除，列为后续迭代（第一期允许「重新建组」人工兜底）。

## 7. 关键行为明细

### 7.1 去重时序（典型场景）

A、B 同局域网且都连着中继。A 复制文本 X：

1. LAN 直连：B 约几十 ms 后收到，入库（hash(X) 无重复 → INSERT）。
2. Relay 中转：B 约几百 ms 后再收到，`store_remote` 按 hash 命中已有记录，
   仅 touch 时间戳，用户无感知。

反向（Relay 先到 LAN 后到）同理。

### 7.2 传递同步与回环

- B 从 Relay 收到 origin=A 的条目，入库时保留 `remote_device_id=A`。
- B 的 `/clips` 会把该条目提供给 C（origin 仍是 A）——中继场景下 C 可能本来就
  会从 Relay 收到，两份同样按 hash 判重，无重复。
- A 无论从哪条通道看到自己发出的条目（origin=A），接收侧直接拒收（§3.2）。

### 7.3 大文件策略（M5 已实现）

图片/大文件经中继会显著消耗服务器带宽，提供开关 `relay.sync_image`
（默认关闭）：

- 关闭时：仅文本走中继；图片/文件仅 LAN。
- 开启时：≤4MB 的 PNG 图片也经中继（base64 内嵌 clip，加密同样生效）；
  超限图片与文件类仍仅 LAN。
- 服务器侧有单条消息硬上限（8MB）兜底。

### 7.4 设备卡合并与「LAN 优先显示」（M5 已实现）

两条通道的设备身份是同一个 `device_id`（首次启动生成后固定不变），它就是合并键。
后端组 `DeviceDto` 时完成合并：`via` 字段标记可达通道（`lan` / `relay` / `lan+relay`），
同一台设备只出一张卡；云端在线即视为在线。前端徽标：双通道显示「局域网+云端」、
仅云端显示「云端」、纯局域网不标注（LAN 优先语义）。

- 仅云端可达（未局域网配对）的设备卡不提供配对/同步/拉黑等局域网操作。
- 注意两路在线判定的时效差：Relay 断连几秒内即知，LAN 靠 beacon 超时，有延迟窗口
  （设备刚离开局域网时 LAN 侧短暂「看着在线」）。
- **发送不受显示影响**：维持双通道双发（§2），徽标只是展示。不引入「按显示通道
  单发 + 失败降级」的状态机——复杂度高、收益小。

## 9. 风险与开放问题

- **安卓端 ClipDitto 需同步实现 Relay 客户端**，否则手机离开局域网后仍是孤岛。
  协议设计（§4.3）刻意保持与现有线上口径一致，降低双端对齐成本。
- **NAT/防火墙**：客户端只出不进，WSS 443 端口基本无阻碍；公司网络封 WSS 时
  可回落 HTTP 长轮询（列为备选，不首期实现）。
- **服务器单点**：宕机时 Relay 中断但 LAN 不受影响；客户端断线重连即可，无需告警。
- **多服务器/迁移**：分组数据无状态（暂存可丢），换服务器只需改配置中的地址，
  游标错位最多导致一次全量补拉 + 哈希判重，无脏数据。
- **开放问题**：是否需要「群组 > 2 台时的选择性同步」（只与部分设备共享）？
  现有 LAN 逻辑是「配对即全共享」，Relay 首期沿用，后续按需在分组内加设备级开关。
